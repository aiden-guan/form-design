# FORM Design behavioral evaluation scenarios

These are reusable evaluation inputs, not claimed test results. Run them in isolated projects with an agent that has only the packaged skill and the stated input artifacts. Assess the produced artifacts and observed behavior, rather than checking that the answer repeats skill terminology. Record model, host, tools, date, time spent, screenshots, and remaining gaps.

| Scenario | Input | Observable success |
| --- | --- | --- |
| Open creative website | A ceramics studio brief with real name, audience, class data, three permitted photographs, existing frontend | Makes a justified direction, implements a runnable page with real content, maintains a clear class/booking path, and visually reviews wide/narrow output. |
| Preserve an existing product | A populated dashboard with working filters and a supplied component library; request typography and density improvements | Improves scan paths and hierarchy without replacing the stack, breaking the filters, inventing data, or adding a marketing hero. |
| Divergent exploration | The same event brief; request three visual directions and a recommendation, no implementation | Produces materially different compositions and explains audience/task tradeoffs. Does not output three palette variants or silently build the site. |
| Faithful reference match | A permitted screenshot at a recorded viewport, actual page copy, available fonts/assets | Preserves visible geometry and content, compares equivalent captures, reports missing evidence, and avoids an unrequested reinterpretation. |
| Native/mobile | A habit-tracker prototype brief, platform target, sample state data | Supports platform navigation, enlarged text, completion/undo, error recovery, reduced motion, and touch without hidden hover requirements. |
| Offline / no shell | A creative brief, packaged writing only; no network, browser, or script execution | Delivers useful design work using the written methods and honestly distinguishes uninspected references and unverified output. |
| Narrow edit | An existing primary button; request pressed/focus states only | Fixes the requested states within the existing system without a large discovery phase, dependency additions, or unrelated page redesign. |
| Source boundary | A reference-only result with an attractive recording; request to recreate its behavior | Uses observation and original implementation, retains source credit where appropriate, and does not claim the recording provides reusable source. |

For creative scenarios, compare against a run with the same model, brief, assets, tools, and time budget but without this skill. Review purpose, composition, distinctiveness, typography, interaction, inclusion, and technical fit using actual output. Subjective comparisons should include examples and reasons; do not convert a single preference vote into a broad quality claim.

If independent agents are used, the evaluator should receive the raw request and artifacts without the intended visual answer or the author's self-assessment. Implementation tests and archive checks do not substitute for this behavioral evaluation.
