# From diagnosis to an observable correction

## One cause can produce many tells

Do not treat the 19 signals as independent tickets. A heading, eyebrow, pill, divider, and italic phrase may all result from one problem: the section has no clear communication job. Decide what that section needs to convey, then rebuild its hierarchy around the answer.

| Cause | Example diagnosis | Scoped repair | Preservation check |
| --- | --- | --- | --- |
| Redundant meaning | Label, heading, and paragraph repeat a category without explaining the offering. | Keep a specific heading and one informative detail; name the useful action. | Necessary facts and qualifiers still exist. |
| Equal visual weight | Decorative metrics and cards compete with the task. | Promote the relevant content; reduce contrast or rearrange secondary material. | The user can still find secondary actions and compare required values. |
| Unrelated style | Terminal art and code labels have no connection to a pottery workshop. | Use the workshop's actual work/process and task vocabulary. | Preserve a technical direction if explicitly requested; do not replace chosen style by assumption. |
| Fragmented grouping | Each sentence has a separate bordered card. | Group by shared purpose using alignment/proximity; retain independent objects as objects. | Inputs, selected items, and actionable regions remain identifiable. |
| Arbitrary type/color | Thin italic display type and faded text carry all roles alike. | Establish role contrast and compare real specimens/semantic colors. | Preserve chosen families and palette; test actual text and states. |
| Simulated sophistication | A beautiful dashboard mockup implies features/data that do not exist. | Use honest product evidence or clearly labeled sample content. | The result does not misrepresent business facts or functional integrations. |

## A practical correction pass

Inspect the actual artifact and write the few observations with the largest consequences. Choose a related set of corrections, not a long shopping list. Work within the existing components and token conventions. Rebuild a composition only when the problem and authorized scope require it.

For an implementation request, make the changes before writing the final critique. For critique-only, provide actionable recommendations without editing. Use before/after captures when tools permit, at equal viewport, crop, fonts, content, and state. A screenshot comparison supports appearance; operate the actions to verify behavior.

Avoid trading a functional affordance for a cleaner screenshot. Test selected filters, status labels, input boundaries, errors, focus, and the amount of information needed to work. A professional comparison table may become worse if every divider or identifier is deleted.

## Controlled alternatives

If two repairs are equally plausible, build a small comparison that answers the remaining question. Keep unrelated variables constant. A font comparison needs the same actual content and layout; a composition comparison needs equivalent factual content and task states. Explain each alternative's cost.

If the user asks to select fonts/colors, preserve that decision as approved context after they choose. If they ask you to choose and implement, make a reasoned choice and finish. Do not add a mandatory selection gate to a task that already authorizes a choice.

## Report with evidence

Prefer “the pale account status is difficult to distinguish from supporting text on this surface; increase role contrast while keeping the status label” to “reduce slop.” Label subjective judgments and missing measurements. Briefly mention significant elements retained for a reason, especially when they appear on the checklist.

Do not claim an aesthetic improvement from counts alone. The useful question is whether the result better expresses the subject and supports its task at the relevant sizes and states.
